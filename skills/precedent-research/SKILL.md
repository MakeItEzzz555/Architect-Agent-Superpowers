# Architectural Precedent Research

Use precedents as evidence and transferable lessons, not as designs to copy.

## Preflight

- Project type, scale, climate, site/context and design question.
- Which attributes matter: plan, section, circulation, facade, structure, envelope, material, public realm, flexibility, sustainability or delivery.

Keep verified facts, project assumptions, design options, and unresolved questions visibly separate. If a required input is absent, record it as `UNKNOWN` rather than inventing it.

## Workflow

1. Find primary project sources, architect/engineer documentation, reputable publications and drawings where legally available.
2. Extract comparable facts into a matrix; distinguish documented fact from visual interpretation.
3. Identify transferable principles and failure risks; explain why each precedent is relevant to this project.
4. Translate findings into design criteria rather than stylistic imitation.

## Deliverables

- Sourced precedent matrix
- Diagram brief for plan/section/massing comparisons
- Transferable principles
- Open questions and evidence gaps

## Verification

- Citations identify project/source and date where available.
- Do not infer hidden structural, cost or performance data from photographs.

For file/model changes, compare the result against a pre-change baseline and report changed items, skipped items, failures, and checks actually run.

## Professional boundaries

- Respect copyright; summarize and diagram rather than reproducing protected drawing sets.
- Do not present resemblance to a precedent as proof of performance or compliance.

If a live CAD/BIM/GIS/analysis tool or MCP integration is available, inspect the current document/model and tool version before write operations. Prefer read-only inspection, dry runs, bounded samples, new output paths, and native undo/transaction mechanisms. Never claim a model or drawing was changed unless the tool confirms it.

If the native application is unavailable, produce a reproducible plan, script, structured data, SVG/DXF artifact, or exact in-application procedure instead of pretending to have operated the software.
